# 记账识别协议修复（2026-09-29）

**状态：用户已确认设计方向；仅真源设计，未修改接口、未部署、未完成真实识别验收。**

## 证据与边界

- 线上 `/api/bookkeeping/understand` 对疑似多笔、复核仅一笔返回 422 `INCOMPLETE_MULTI_ORDER`。最近同页五次识别均命中该规则，DeepSeek 四次、豆包一次。
- `/api/bookkeeping/rerecognize` 要求元数据 `categories` 为数组，但当前 Android 遵循自主分类规则而不发送该字段；六次图片请求均在解析阶段返回 400，未调用视觉模型。
- 用户期望确认一笔先保存并提示可能漏单，点击重新识别后上传截图获取多笔。旧版 0.1.56 不能显示漏单警告，故不能直接对所有客户端启用部分确认。

## 两阶段接口合同

1. 图片接口允许 `categories` 缺席，规范化为空列表；显式存在时仍按原有限长和分类元素结构验证，`null`、对象及超限无效。认证、图片格式/大小、请求 ID、模型路由不变。Android 不为满足旧校验而上传本地分类候选。
2. 文字接口以 `X-Bookkeeping-Partial-Order: 1` 作为显式能力声明。仅当该标识精确匹配、疑似多笔、复核后恰有一笔完整有效草稿时返回 HTTP 200 和 `warnings: ["POSSIBLE_INCOMPLETE_MULTI_ORDER"]`。无标识或未知值继续 422；多笔正常返回全部；零有效草稿及上游故障保持失败。能力标识不能由 User-Agent 或版本号推断。

Android 侧完整设计见记账 App 仓库 `docs/superpowers/specs/2026-09-29-recognition-protocol-repair-design.md`。本次不引入新的模型、SDK、密钥、数据库表或截图保存策略。

## 验收与发布

- 合同测试覆盖缺席/合法/非法 `categories` 以及能力标识有/无/未知值、单笔/多笔/零笔路径。
- 测试请求用非真实账单材料；日志不得包含截图、OCR 正文、API 密钥或分类目录。
- 分阶段发布，先备份及核验回滚，再修图片接口并检查旧版兼容；新版 Android 安装和能力验收后，才切换带能力隔离的文字合同。
- 每次生产切换前另行取得用户明确授权。真实手机图片重识别、多对话框与逐笔删除前均标记为未验证。
