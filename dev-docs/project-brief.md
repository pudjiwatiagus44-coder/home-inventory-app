# Project Brief

## 项目边界

- 项目名称：Home Inventory App。
- 中文名称：家庭物品管理应用。
- 项目是什么：一个面向普通家庭用户的云端 Web/PWA 应用，用户注册登录后可以记录、搜索、编辑和删除自己的家庭物品，并可与家人共享同一个家庭空间共同维护。
- 项目不是什么：不是当前局域网单 JSON 本地版的直接改造；不是第一阶段就做原生 App、高清原图上传、扫码识别或会员付费（2026-08-07 起 Android 内测版包含拍照识别：服务器仅保存缩略图，识别用清晰图保存在手机本地）。
- 第一批用户：希望用手机或电脑管理家中物品位置、备注和过期日的个人用户。
- 使用场景：用户想知道某个物品放在哪里、某个位置有什么物品、哪些物品快过期。
- 一句话定位：给每个家庭一个可搜索、可维护、可长期保存的云端物品清单。
- 交付对象：未来公开用户；当前阶段先做 MVP 原型。

## 用户问题和价值

- 用户痛点：家中小物品、药品、食品、工具和备件散落在不同位置，时间久了找不到、忘记过期、重复购买。
- 为什么值得做：当前本地版已经证明“位置 + 物品 + 搜索 + 过期提醒”是有效核心模型，云端版可以让更多用户直接使用。
- 参考来源：当前本地版置物管理系统的数据模型和使用体验。
- 可以学习的地方：格子/区域管理、搜索、过期提醒、移动端优先。
- 不能照搬的地方：单 JSON 文件、局域网可信环境、无账号假设。
- 差异点：第一版专注低成本记录和快速查找，不追求复杂家庭资产管理、装修库存或企业仓储。

## 第一闭环

```text
用户注册/登录
  -> 创建第一个位置
  -> 新增一个物品
  -> 搜索该物品或按位置查看
  -> 编辑/删除物品
  -> 数据保存到该用户自己的云端空间
```

- 第一闭环输入：邮箱、密码、位置名称、物品名称、备注、过期日。
- 第一闭环输出：用户只能看到自己的位置和物品，并能搜索查询。
- 用户可见成功标准：刷新浏览器或换设备登录后，自己的物品仍然存在。
- 失败时用户会看到：登录失败、保存失败、权限不足、网络异常等明确提示。

## MVP 范围

第一版必须有：

- 邮箱 + 密码注册登录。
- 登录用户私有数据隔离。
- 家庭共享：房主创建家庭空间，生成邀请链接并通过微信等渠道发给家人；家人打开链接提交加入申请，房主批准后成为成员，与房主共同查看、编辑家庭里的区域、位置和物品；房主可以移除成员。
- 邀请链接落地页包含 Android 内测版 App 下载入口，方便尚未安装 App 的家人先下载再申请加入。
- 位置管理：新增、编辑、删除、排序暂不要求。
- 物品管理：新增、编辑、删除。
- 搜索物品。
- 按位置查看物品。
- 过期日字段和基础过期提示。
- 响应式 Web/PWA 基础体验。

第一版可以没有：

- 高清原图上传（2026-08-07 起拍照识别阶段服务器仅保存缩略图；识别用 1280px 清晰图保存在手机本地）。
- 扫码识别。
- 会员付费。
- 原生 iOS/Android。
- 管理员后台。
- 多语言。

后续再做：

- 高清原图与多附件（当前仅保存物品缩略图）。
- 条码/二维码扫描。
- 到期通知。
- 导入当前本地版 JSON 数据。
- 付费会员和容量限制。

## 不做什么

- 第一阶段明确不做手机号短信登录。
- 第一阶段明确不做高清原图上传；2026-08-07 确认 Android 内测版新增拍照识别，服务器只保存物品缩略图（约 5–15KB/张）；识别用图（1280px 压缩图）在手机本地保存一份用于放大查看，服务器不保存原图。
- 第一阶段明确不做真实支付。
- 第一阶段明确不做原生 App。
- 家庭共享第一版不做真实邮件/短信通知：邀请链接由房主生成后通过微信等外部渠道手动发送，不接入微信开放平台或微信授权登录。
- 邀请链接默认 30 天有效，可在家庭设置中作废或重新生成；同一家庭同一时间只有一个有效邀请链接。
- 加入申请需要房主批准：申请人提交申请后处于 pending，批准前不拥有任何家庭数据访问权。
- 家庭共享第一版不做房主转让、成员自助退出、多家庭并行数据合并；一个账号可属于多个家庭，UI 通过“当前家庭”切换器选择操作哪个家庭。
- 不把当前本地版 `server.py + shared_data.json` 强行迁移成多用户架构。

## 关键风险

- 登录/权限：用户数据必须按账号隔离，后端/数据库权限必须兜底。
- 支付/会员：第一版不做，仅预留未来边界。
- 上传/文件/隐私：第一版只保存物品缩略图，不上传高清原图；识别瞬间照片会发送给第三方 AI 服务商（火山引擎），公开推广前隐私政策必须写明。
- 第三方 API/SDK：当前主线不再使用 Supabase；服务端外部依赖仅按已确认范围使用 QQ SMTP、火山引擎豆包等，凭据只存服务器环境变量。
- 生产环境/真实用户：上线前必须补齐隐私政策、数据删除、备份恢复和监控。

## 验收标准

- 用户可以注册、登录、退出。
- 不在同一家庭的用户 B 无法读取、修改或删除用户 A 家庭的物品。
- 同一家庭的成员可以查看、新增、编辑、删除家庭内的区域、位置和物品。
- 房主可以生成邀请链接发给家人；家人打开链接提交申请，房主批准后成为成员，批准前不能访问家庭数据。
- 邀请链接落地页可以下载 Android 内测版 App；App 登录后可继续完成申请加入。
- 被移除的成员立即失去访问权，家庭数据仍保留。
- 用户新增物品后刷新页面仍存在。
- 用户可以搜索物品并看到正确位置。
- 用户可以设置过期日并看到基础提醒。
- 所有真实数据来自阿里云自托管 PostgreSQL 和服务端 API，不使用 mock 数据冒充完成。

## 停止条件

- 尚未完成数据库 schema 和服务端权限策略设计，不进入功能开发。
- 尚未确认自托管环境变量、数据库和服务端权限边界，不接入真实云服务。
- 尚未完成权限负例验证，不声明 MVP 安全可用。

## 2026-08-06 家庭成员共享决策

用户确认将“家庭成员共享”从后续再做调整到当前阶段范围，按建议默认方案先行 Web/PWA：

- 邀请方式：房主在家庭设置中生成邀请链接（带随机 token，默认 30 天有效），通过微信等渠道发给对方；链接落地页展示家庭名称、“申请加入”按钮和 Android 内测版 App 下载入口；对方打开链接注册/登录后提交加入申请，房主批准后成为成员。第一版不发送真实邮件，不接入微信授权或微信开放平台。
- 权限模型：`owner` 与 `member` 对家庭内区域、位置、物品拥有相同的查看/新增/编辑/删除权限；只有 `owner` 能邀请成员、移除成员、更新和删除家庭。
- 数据归属：数据属于 `household`，不属于个人；成员被移除后立即失去访问权，数据保留在家庭内。
- 家庭形态：一个账号可属于多个家庭（自己注册时创建的默认家庭 + 被邀请加入的家庭）；第一版 UI 提供“当前家庭”切换器，所有清单操作基于当前家庭。
- 边界：第一版不做真实邮件/短信通知、房主转让、成员自助退出、多家庭数据合并；不接入微信授权；Android 内测版提供房主生成邀请链接并分享、批准/拒绝加入申请，以及当前家庭切换/查看共享家庭清单的能力（成员管理等仍以 Web 端为主），邀请链接页提供 APK 下载入口。
- 实施路线：直接在自托管部署（`homestorag.xyz`，自有 PostgreSQL + 自有认证/服务端权限）上实现并上线，不以 Supabase 为实施目标；Supabase 历史方案已于 2026-08-11 归档，默认不再读取。
- 架构与数据设计见 `dev-docs/architecture.md`、`dev-docs/database-design.md`；实施计划见 `dev-docs/stages/family-sharing.md`（设计已确认，尚未进入代码实施）。

## 2026-08-04 Excel 批量备份与导入规则

- Excel 批量备份与批量导入作为上线后清单维护能力纳入当前 Web/PWA 产品范围。
- 备份和导入均使用 `物品清单` 工作表，表头为 `序号 / 名称 / 格子编号 / 所在区域 / 备注 / 有效期`，兼容参考文件 `物品清单_2026-08-03_17-02-39.xlsx`。
- 备份文件名使用 `物品清单_YYYY-MM-DD_HH-mm-ss.xlsx`。
- 导入必须先预检，不直接写入数据库。
- 预检以 `所在区域 + 格子编号 + 名称` 作为同格同名物品判断键。
- 有效期支持 `YYYY-MM-DD` 和 `YYYY-MM`；当 Excel 只有年月、没有日单位时，默认按该月 1 号导入。
- 如果同格同名物品的备注和有效期也完全相同，自动跳过。
- 如果同格同名物品的备注或有效期不同，弹窗展示当前数据与 Excel 数据对比，由用户选择跳过、都保留或覆盖。
- 全新物品自动导入；缺失的区域和格子由导入流程自动创建。
- 覆盖只更新已有物品的备注和有效期，不改变名称、区域或格子。
- 导入完成后显示新增物品数、覆盖数、保留重复数、跳过数、新增区域数、新增格子数和失败行。

## 2026-08-04 Android 原生内测版规划

- 用户已确认新增 Android 原生 App 产品线：先做 Android 内测 APK，后续再单独规划 iOS。
- Android 第一阶段采用 Kotlin 原生实现，不采用 React Native/Expo，也不采用 WebView 套壳。
- Android 内测版复用现有邮箱 + 密码账号、后端 session、库存 API 和权限边界；不单独建立移动端账号系统。
- Android 内测版包含离线缓存与离线编辑能力：最近一次同步后的清单可离线查看，离线时可新增、编辑、删除区域、位置和物品。
- 离线新增在网络恢复后应自动尽快同步到服务器；同步成功后用服务器返回的真实 id 和更新时间替换本地临时状态。
- 离线编辑和删除采用服务器优先冲突策略：如果服务器数据已变化，Android 不自动覆盖服务器，而是提示用户刷新后重新确认。
- Android 内测 APK 托管在阿里云测试服务器静态目录，下载地址固定指向最新版本；每次 Android 构建后自动上传新 APK 并更新版本信息，App 启动时检查版本并提示下载更新（受 Android 系统限制，安装需用户确认，不做静默安装）。
- 本阶段仍不加入高清原图上传、扫码识别、推送通知、支付、管理员后台、应用商店上架或 iOS 实现；2026-08-07 确认新增拍照识别（服务器仅保存缩略图，清晰图存手机本地）。
- 家庭共享先做 Web/PWA（2026-08-06 已确认）；Android 内测版包含房主邀请分享、申请审批和当前家庭切换能力：在 App 内生成邀请链接并通过系统分享/复制发给家人，家人申请后房主直接在 App 内批准或拒绝；共享成员点顶部家庭名称切换并查看被邀请的家庭清单，链接落地页提供 Android 内测 APK 下载入口；APK 由服务器托管、每次构建后自动更新，下载地址为部署配置项（第一版不接应用商店）。

## 2026-08-07 拍照识别物品决策（Android 内测版先行）

用户确认将「拍照识别物品」纳入 Android 内测版阶段范围，从「不做」清单中移出照片上传与 AI 图片识别两项（仍不做高清原图与扫码识别）：

- 功能形态：拍物品正面照识别名称自动填表；可选拍有效期照片识别过期日（该照片不保存）。
- 存储：服务器只保存物品缩略图（160–200px、约 5–15KB）；识别用图（1280px 压缩图）在手机本地保存一份用于放大查看（换设备/重装后不可恢复，回退服务器缩略图）；第一版缩略图存服务器本地磁盘并预留存储抽象层，后续数据量上来再切 OSS。
- AI 服务：火山引擎豆包视觉，API key 仅存服务器；单次识别成本约 0.005–0.02 元，用户确认可接受。
- 识别链路：App 本地压缩（约 1280px、200–400KB）→ 上传服务器 → 服务器生成缩略图暂存并调豆包 → 返回名称/日期与缩略图 id → 保存物品时关联。
- 实施端：Android 内测版先行，Web/PWA 后续。
- 设计文档：`docs/superpowers/specs/2026-08-07-photo-recognition-design.md`；架构与数据设计见 `dev-docs/architecture.md`、`dev-docs/database-design.md`。

## 2026-08-08 登录页增强与密码重置决策

用户反馈登录页缺少「忘记密码」「记住密码」，Android 缺少注册入口；对话确认以下决策（2026-08-08）：

- 忘记密码：接邮箱发送重置链接。服务器配置 SMTP（QQ 邮箱 `smtp.qq.com` + 授权码），凭据只存服务器 `app.env`，不进仓库。
